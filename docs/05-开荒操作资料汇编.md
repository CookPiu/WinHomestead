## 1. 建议纳入：Dev Drive（官方，优先级最高）

微软官方为开发负载提供的存储卷形态，与本工具 3.2 目录骨架、3.4 开发缓存预设正面相关，现有清单完全没有涉及。

| 事实 | 内容 |
|---|---|
| 本质 | ReFS 卷 + 信任标记，Defender 在其上跑 performance mode（异步扫描），不是排除项 |
| 前置 | Windows 11 Build 10.0.22621.2338+，建议 16GB 内存（最低 8GB），至少 50GB 可用空间，需管理员，全 SKU 可用 |
| 创建 | 设置 → 系统 → 存储 → 高级存储设置 → 磁盘和卷 → 创建开发驱动器；或 `Format D: /DevDrv /Q`、`Format-Volume -DriveLetter D -DevDrive` |
| 三种载体 | 新建 VHDX（推荐动态扩展）、压缩现有卷、使用未分配空间 |
| 关键限制 | **只能在格式化时指定，现有卷无法就地转换**（转换等于抹掉数据）；C 盘不能是 Dev Drive；可移动磁盘不支持；动态磁盘不支持；最小 50GB |
| 建议存放 | 源码仓库、包管理器缓存、编译产物与中间文件 |
| 不建议 | 安装应用程序、SDK 与开发工具本体（官方明确建议装在 C 盘） |
| 信任与检查 | `fsutil devdrv trust D:`、`fsutil devdrv query D:`；卷换机器后信任标记不跟随 |
| 24H2 起 | 支持 block cloning，复制文件走元数据操作 |
| BitLocker | 宿主卷加密时 VHD 随之加密，不需要单独对挂载卷开 BitLocker |

对本项目的三点直接影响：

1. **与 3.4 的关系是互补而非替代**。Dev Drive 解决「缓存读写快不快、杀软扫不扫」，3.4 解决「缓存落不落 C 盘」。两者都靠同一批环境变量落地，工具可以在数据盘是 Dev Drive 时把缓存指过去，不是 Dev Drive 时照旧指到 NTFS 数据盘。
2. **TEMP 迁移有一条官方风险提示需要补进 3.3**：把 `%TEMP%` / `%TMP%` 指到 Dev Drive 时必须放行 `WinSetupMon` 过滤器，否则影响 Windows 升级流程；官方原话还提醒「很多程序用这两个变量，注意副作用」。
3. **本机场景是「建议 + 检测」而非「执行」**。D 盘已是 NTFS 且有数据，不可能就地转 Dev Drive。工具能做的是：检测数据盘是否已是 Dev Drive（`fsutil devdrv query`），未分配空间是否够 50GB，够就给出创建入口与说明，不够就只说明。

来源：[Set up a Dev Drive on Windows 11 - Microsoft Learn](https://learn.microsoft.com/en-us/windows/dev-drive/)

## 2. 建议纳入：对 3.4 缓存变量表的事实性修正与补充

官方 Dev Drive 文档给出的包缓存迁移清单，与 `01-范围清单.md` 3.4 对照后有三处需要改：

| 项 | 清单现状 | 官方事实 | 建议 |
|---|---|---|---|
| Maven | 列在「不做」，理由「只能改 settings.xml，没有环境变量入口」 | 官方给出 `MAVEN_OPTS="-Dmaven.repo.local=D:\packages\maven"`，等价于本地仓库改址 | **理由不成立，应改**。是否纳入执行项另说（Maven 用户通常已有 settings.xml），但文档里的判断要更正 |
| vcpkg | 未收录 | `VCPKG_DEFAULT_BINARY_CACHE`，默认位置 `%LOCALAPPDATA%\vcpkg\archives` | 建议补进 3.4 变量表，C++ 开发者受益 |
| NuGet | 已收录 `NUGET_PACKAGES` | 官方提示：该变量会**覆盖** nuget.config 里的 `globalPackagesFolder`，包括仓库自带的配置；官方推荐优先用配置文件 | 变量保留，但要在风险文案里写清这条覆盖语义 |

另：官方文档一律用 `setx /M`（Machine 作用域，需管理员）。本工具用 User 作用域是有意的选择（免管理员、可回滚），与官方差异应在文档中说明，不是错误。

来源：[Set up a Dev Drive on Windows 11 - Microsoft Learn](https://learn.microsoft.com/en-us/windows/dev-drive/)

## 3. 建议纳入：Point-in-time restore（26H2 默认开启，影响系统盘空间）

Windows 11 26H2（2026 年 10 月发布，以启用包形式交付，与 25H2 同平台）把 Point-in-time restore 默认打开。要点：捕获系统状态（Windows 本体、已装应用、设置、系统盘上的本地文件、密码、证书、密钥），还原点存在本机，**最多占用 50GB**，保留 72 小时并自动刷新。设置备份云同步同期改为默认开启，但仅限 Microsoft Entra 管理设备且不含欧盟 DMA 地区。

对本项目的影响：新机在 26H2 上会有一块最大 50GB 的系统盘占用凭空出现，而本工具 3.6「空间清理」和收尾的「创建还原点」都直接踩在这块地上。至少要做到：在「这台电脑」或空间清理分类里检测该功能状态与实际占用，向用户说明这 50GB 是什么；工具自己创建的还原点与它的关系也要在文案里交代清楚。

新机上市时间决定了这条很快会成为默认场景，优先级不低。

来源：[Windows 11 26H2 auto-enables point-in-time restore - Windows Latest](https://www.windowslatest.com/2026/08/21/windows-11-26h2-will-auto-enable-point-in-time-restore-by-default-how-to-check-yours/)、[Windows 11 26H2 ships as enablement package - gHacks](https://www.ghacks.net/2026/08/10/windows-11-26h2-ships-as-an-enablement-package-with-movable-taskbar-local-search-and-default-cloud-recovery/)、[Windows 11, version 26H1 - Microsoft Support](https://support.microsoft.com/en-us/servicing/os/windows/2026/02/windows-11-version-26h1)

## 4. 建议纳入「检查项」子页的只读新增项

都符合 4.4 既定原则：只检测、只说明、只跳转，不代改。

| 候选项 | 检测方式 | 判定/说明 | 跳转 |
|---|---|---|---|
| 刷新率未拉满 | `EnumDisplaySettings` 取当前刷新率与该分辨率下支持的最大值 | 高刷屏默认跑 60Hz 是新机常见状态，媒体清单里几乎每篇都列 | `ms-settings:display-advanced` |
| 启动项 | `Win32_StartupCommand` 或 Run 键 + 启动文件夹 | 列出 OEM 预装自启项，用不上的自行关掉；与 4.4 的 OEM 预装软件项天然配套 | `ms-settings:startupapps` |
| 电池健康（笔记本） | `powercfg /batteryreport` 生成 HTML，取设计容量、满充容量、循环次数 | 新机刚装完数据不足，报告需正常使用几天才有参考价值——这条限制要写进文案，否则会误导 | 打开生成的报告 |
| BitLocker 密钥保存位置 | 已有的 `Win32_EncryptableVolume` 检测上补一句文案 | 密钥必须存在本机以外：微软账户、打印件、U 盘皆可，但不要把 U 盘和本机放一起 | `ms-settings:deviceencryption` |
| Point-in-time restore 占用 | 见第 3 节 | 说明这块空间是什么、能不能关 | 设置 → 系统 → 恢复 |

刷新率与 HDR 的补充事实：笔记本在电池供电下默认会关闭 HDR，需要在电源设置里单独允许；HDR 开启后观感发白属于需要跑「HDR 显示器校准」应用而非故障。这两条适合作为文案而不是执行项。

来源：[HDR settings in Windows - Microsoft Support](https://support.microsoft.com/en-us/windows/hardware/display-graphics/hdr-settings-in-windows)、[Powercfg 命令行选项 - Microsoft Learn](https://learn.microsoft.com/zh-cn/windows-hardware/design/device-experiences/powercfg-command-line-options)、[Backup BitLocker recovery key - Pureinfotech](https://pureinfotech.com/backup-bitlocker-recovery-key-windows-11/)、[4 settings I always change on a new monitor - XDA](https://www.xda-developers.com/settings-i-always-change-on-a-new-monitor/)

## 6. 搜到但明确不纳入

| 项 | 外部来源的说法 | 不纳入的理由 |
|---|---|---|
| 第三方 debloat 脚本 / IObit Uninstaller 批量卸载预装 | 多篇清单推荐 | 与「微软服务与预装应用默认保留」冲突；第三方脚本不可控 |
| Driver Booster / Snappy Driver 等驱动更新工具 | MajorGeeks 等推荐 | 驱动只应来自 OEM 与 Windows Update，第三方驱动库风险不对称；工具可以在软件推荐页给 OEM 支持页链接，但不推荐这类软件 |
| 关闭内存完整性（HVCI）换游戏性能 | Pureinfotech 列为 gaming performance | 安全项不动，v1 已删除 |
| 暂停更新两周 / 关闭「尽快获取最新更新」 | MajorGeeks 第 2 条 | 属于 Windows Update 策略，v2 已明确不碰 |
| UTF-8 Beta「全球语言支持」 | 中文社区大量文章讨论 | 开启会让 GB18030 编码的旧压缩包与老程序乱码，只对少数 Linux 移植程序有益。**不做执行项**，如果要收录只能作为检查项里的「不要动」说明 |
| OOBE 跳过微软账号（`oobe\bypassnro`） | 中文「开荒」文章几乎必写 | 发生在系统安装阶段，本工具运行时已经过了那一步；且微软自 Build 26120.3653/26200.5516 起移除该命令，各类替代法随版本失效，写进工具只会过期 |

## 7. 处理结果（2026-09-11 已落地）

第 1–4 节的四项全部纳入，范围清单与实现同步更新：

| 项 | 落地形态 | 代码 |
|---|---|---|
| Dev Drive | 「分区」分类新增 `disk.devdrive`，PromptOnly：检测数据盘文件系统与未分配空间，给建议与步骤，不格式化任何卷。MDM 下列出并标不适用 | `DevDriveTasks.cs`，`IStorage.FileSystemOf` / `LargestFreeExtent` |
| 缓存变量修正 | `env.preset` 补 `MAVEN_OPTS`（值为 `-Dmaven.repo.local=<路径>`）与 `VCPKG_DEFAULT_BINARY_CACHE`；NuGet 覆盖语义与 MAVEN_OPTS 的注意事项写进条目说明；Maven 从「不做」表移除 | `DevCacheTasks.cs`，`SnapshotCollector` 增加 vcpkg 探测 |
| 26H2 还原点占用 | 检查项新增一条，按 Build 与系统卷容量说明会不会被自动开启，跳转 `ms-settings:recovery`。没有公开接口能读开关，文案如实说明 | `SystemChecks.PointInTimeRestore` |
| 检查项扩容 | 六项 → 十项，新增还原点占用、开机启动项、屏幕刷新率、电池健康 | `SystemChecks`、`DisplayInfo`、`BatteryProbe` |

实现期间两处与原计划不同，都是实测后改的：

1. 电池健康原计划只读 `root\WMI`，本机实测 `BatteryStaticData` 直接报「常规故障」拿不到设计容量，所以加了一层 `powercfg /batteryreport /xml` 回退（不需要管理员，临时文件读完即删）。
2. Dev Drive 原计划在 MDM 机器上直接不列出，改为列出并说明原因——企业策略是环境限制不是「不需要」，让条目凭空消失不如给一行原因。
